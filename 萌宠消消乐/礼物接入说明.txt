两款小游戏 · 菘蓝整蛊机 / 白曜重工礼物接入

设置入口：S / F2 → ③ 礼物与互动。

一、直接导入宿主（与抓萌宠 V1.0.41 一样）
1. 把对应的离线单文件 HTML 导入菘蓝「自定义插件」或白曜重工 HTML 插件。
2. 默认接收真实礼物，规则来源选择「插件内礼物绑定」。填写礼物名称、每个礼物触发次数；留空不接这件礼物。
3. 菘蓝和白曜都可以使用插件内绑定，无须另外配置白曜规则。
4. 优先订阅 SonglanPlugin.onGift；白曜为兼容菘蓝也提供该接口。缺少时再使用 BaiyaoPlugin.onGift，同一份礼物只订阅一个入口。
5. 初始绑定只是可编辑的默认值，请按直播间实际礼物名称调整。相同礼物名不能同时绑定两种效果。

二、OBS 本地文件 / 独立浏览器
没有宿主注入 SDK 时，在「接入方式、本机转发与白曜动作 ID」中手动勾选「启用本机礼物转发」。
宿主的本机转发服务须已开启。当前菘蓝默认 9910，白曜菘蓝兼容转发支持 9910 / 10030；端口按宿主实际设置填写。
只连接 ws://localhost:所填端口，发送 identify 标识并接收礼物，不向宿主广播模拟礼物。
这个端口只接礼物；加班走白曜加班机，不用这里设。
如果宿主 SDK 稍后出现，会自动关闭本机转发，改用 SDK，避免双通道重复。

三、可选：由白曜规则控制
把规则来源切成「白曜重工规则动作」，在白曜为当前 HTML 插件建立规则。
「插件动作」填写设置中列出的动作 ID，如 bomb、ice、reverse 等；「动作数值」是次数，宿主 repeat 会一起相乘。
该模式使用 BaiyaoPlugin.onAction。启用后，插件内普通礼物绑定不再执行，避免一件礼物触发两遍。

四、数量与候场
白曜提供的 count 已是本次新增数量，直接按增量处理；例如 1、2、3 共执行 6 次。
只有明确标记累计且带 comboId 时才做差；累计 1、2、3 共执行 3 次。effectiveGiftCount 优先作为增量。
有 eventId / msgId 的消息去重；无事件 ID 的独立礼物不按昵称和数量擅自合并，转发方重发而又不提供 ID 时无法保证辨认重发。
游戏忙、暂停、等待开始时先候场。一次执行一个效果；最多 2,000 次、100 条，超出数量显示为未接纳。
未执行候场超过 120 秒按真实时间过期，数量显示在面板里。重开或结束本局清理旧候场；刷新不恢复或重放。
关掉接收开关会清理候场并拒绝新的真实输入，手动测试仍可用。

五、确认状态
「SDK 已绑定」表示宿主接口已订阅；收到礼物后，收到件数、执行次数、候场数和最后一条记录会更新。
只有「本机转发已连接」才表示本机 WebSocket 已接通；单独打开且未开启转发时显示未检测到 SDK。
每行 ▶ 是本页模拟，不会给其他插件广播礼物，但会影响当前棋盘。模拟与真实礼物使用同一执行入口。
目前已完成真实宿主协议的隔离回放、去重/连送/排队测试和隔离 WebSocket 收发测试；未宣称已完成真实直播间送礼或 OBS 实机联调。

预览底色开关已统一为「已开启 / 已关闭」，默认关闭，关闭后恢复透明；该预览状态不随刷新保存。

六、宿主消息解析测试
设置 → ③ 礼物与互动 → 展开「宿主消息解析测试」。
选择「菘蓝端口」或「白曜端口」，自动载入与当前绑定匹配的礼物样例；也可以粘贴实际收到的原始 JSON。另有白曜 SDK 礼物回调和白曜规则动作样例。
「解析检查」只读检查消息，显示礼物、观众、数量、增量、匹配效果和应触发次数，不改变棋盘和测试记录。
「模拟收到」使用正式接收逻辑，并记住测试消息 ID / 累计连击；重复点击同一 ID 会提示重复。默认不会触发棋盘。
勾选「同时触发棋盘效果」后再点「模拟收到」，通过检查的效果才进入当前游戏队列；暂停、候场、容量和过期规则仍然生效，也会按当前游戏规则结算加班。
已模拟接收过的同一 ID 不会因后来勾选触发而重放；点「载入新样例」获得新 ID，或「清空测试记录」后重测。
测试遵循当前接收开关和规则来源。测试去重 / 连击记录与真实礼物隔离，不增加真实收到件数，不保存到磁盘，不向真实端口广播。
测试可以检查解析和效果处理；不能证明实际宿主端口已经连接或直播平台已经发来礼物。真实连接状态仍以上方状态栏为准。
